# 多模型客户端里的三层自我改进

**English version: [architecture-rsi.md](architecture-rsi.md)**

这篇文章里的每一条技术断言都对照本仓库的源码核过，并注明了文件和符号。哪一句和代码不一致，以代码为准，那是这篇文章的 bug。

## 难的不是路由

假设你手上有五份 key。两份是有日额度上限的免费档，一份是网关（`auto/best-coding` 这种逻辑路由，它今天解析到哪个底座模型由它自己说了算），一份是你机器上已经登录的订阅制命令行客户端，还有一份按 token 收费、能不用就不用。

最容易想到的框架是**路由**：给定一个请求，挑最好的模型。这个框架在三个不同的地方是错的，而且正是这三处错误，让大多数多模型工具用起来比写死一份 key 还难受。

**第一，「最好」不是程序能看见的属性。** 程序能量延迟、token 成本和完成情况。它看不见第三条路由要到一号才恢复免费额度，看不见第四条是公司报销的，看不见第五条不能碰某个客户的数据。这些才是真正决定顺序的约束，而它们全部只存在于用户的脑子里。一个替你给路由排名的系统，是在宣称它知道一件它并不知道的事。

**第二，工作单元是任务，不是请求。** 请求是无状态的，按请求在模型之间回落是个已经解决的问题，一个代理二十行就能做。而一个任务已经读了九个文件、问过用户两个问题、写出了一版草稿，并且正跑在第二十分钟上。这时底下的路由死了，「换个模型重试」不是恢复，是一次失忆的重来。这个问题里所有困难的部分，都是关于**换人的时候什么东西能跟着过去**。

**第三，大多数失败不会告诉你它是什么。** 本应用的现场数据里，跑完的任务中大约四分之三根本没有用户判定 —— 没人守在旁边点一下「这个结果可用」。任何要从结果里学东西的系统，都必须决定拿「不知道」这个占多数的情况怎么办，而两个最容易想到的答案（算成功、算失败）都在编造数字。

所以设计问题不是「哪个模型最好」，而是：**程序能从你自己的使用里正当地学到什么，它必须拒绝下什么结论，以及程序和用户之间的那条界线画在哪里。** 这篇文章讲的就是那条界线。

---

## 三层

整个架构按「每一层被允许改变什么」切成三层。

| 层 | 改变什么 | 时间尺度 | 模块 |
|---|---|---|---|
| **执行层** | 眼下这一个任务 | 秒 | `src/lib/failover.ts`、`electron/tools/index.cjs`（`opKeyOf`/`onceOnly`）、`electron/hooks.cjs`、`src/lib/skills.ts` |
| **经验层** | 下一个任务从什么地方开始 | 天到周 | `src/lib/observations.ts`、`src/lib/routing-memory.ts`、`src/lib/skills.ts`（合并） |
| **元层** | 前两层到底有没有在变好 | 周 | `src/lib/evals.ts` |

「递归自我改进」是个被用坏了的词，所以先给出它在这个代码库里的收缩版含义：**系统自己的执行轨迹是它以后做决策的输入，并且存在第三层，它唯一的工作是检查这个回路产出的到底是改进，还是一堆只会往上走的数字。** 这里没有任何东西改写自己的代码，也没有任何东西无人监督地运行。元层之所以存在，恰恰是因为前两层非常擅长制造「在进步」的表象。

三层是按事故半径排的。执行层的 bug 毁掉一个任务；经验层的 bug 会悄悄地把之后几个月的每一个决策都带偏；元层的 bug 意味着你永远不会发现前两个。每往上一层，取舍就更保守一点。

# 第一层 —— 执行

## 1.1 交接：三件事，模块只认领中间那一件

`src/lib/failover.ts` 一共 92 行。它的头部注释把三件事分开，并且明确说自己只做中间那件：

- **策略** —— 换成谁、免费的先上还是贵的先上 —— 归用户。*代码不知道哪条路由是付费的，也不该知道。*
- **触发** —— 这次失败该不该换人 —— 归程序。
- **执行** —— 换人时带什么过去 —— 归程序，但在别处。

所以这个模块不排序、不打分、不挑「最好的」模型。名单是用户自己排的顺序，程序只按那个顺序往下走，并跳过已知坏掉的。名单为空就什么都不做。

这是一个靠做减法做对了很多事的小文件，下面讲它里面的三个决定。

### 三层继承：只有 undefined 才继承

```ts
export function resolveFailover(
  session?: FailoverConfig, project?: FailoverConfig, app?: FailoverConfig,
): { config: FailoverConfig; from: FailoverScope | 'none' } {
  if (session) return { config: session, from: 'session' };
  if (project) return { config: project, from: 'project' };
  if (app)     return { config: app,     from: 'app' };
  return { config: { enabled: false, routes: [] }, from: 'none' };
}
```

会话压过项目，项目压过应用全局。真正吃劲的地方在于「什么叫没设置」：**只有 `undefined` 才往上继承**。已经设置的那一层算数，哪怕它是一个空名单，哪怕它是明确的 `enabled: false`。

源码里给的理由是：「我这一次不想自动交接」和「我这一层没意见」是两句不同的话，必须能分开说 —— 否则用户一旦设了全局默认，就再也没办法为单次任务把它关掉。

这类区分是配置系统最容易不小心抹掉的，通常就抹在「把空集合当成不存在」这一步上。而且一旦抹掉就补不回来了：后面再加一个标志位也没用，因为这两个状态在存储里已经长得一模一样了。

界面把这个区分一路带到了前台（`src/components/FailoverList.tsx`）：每个层级的页签会标出这一层是否有自己的设置，有一行字说明当前实际生效的是哪一层、里面有几条候选，并且有一个明确的「这一层改回继承上层」按钮 —— 它把这一层清掉而不是清空，这是用户在图形界面里唯一能表达 `undefined` 的方式。

### 哪些失败会交接，以及刻意不交接的三类

```ts
export function shouldHandOff(info: ErrorInfo): string | null {
  if (info.blameModel) return '这条路由自己坏了';
  switch (info.kind) {
    case 'rate_limit':
    case 'quota':             return '这条路由的额度暂时用完了';
    case 'auth':
    case 'route_unavailable':
    case 'routing_policy':    return '这条路由当前不可用';
    case 'tools_unsupported': return '这条路由不支持本次任务要用的工具调用';
    case 'multimodal':        return '这条路由看不了图';
    case 'context_too_long':  return '这条路由的上下文窗口装不下';
    case 'network':
    case 'timeout':           return '连接反复不通';
    default: return null;
  }
}
```

函数返回的是**理由**而不是布尔值，`null` 表示「换了也没用」。判断只看错误本身 —— 不看用户偏好，不看成本，不看历史。触发和策略保持分离。

有三类错误落到 `default`，因此永远不触发交接。这是整个文件里最刻意的一个决定，源码写了原因：

- **`bad_param`** —— 请求本身就写错了。每一条路由都会以同样的方式拒绝它。交接只是把一个清楚的 400 变成五个糊涂的 400。
- **`loop_detected`** —— 模型陷进了行为死循环。那是这段对话的属性，不是这条路由的属性。下一个模型继承同一段对话，会做同样的事。
- **`unknown`** —— 谁也说不清原因。源码的原话是：对说不清的错误自动换人，*「只会把整张名单挨个烧一遍，还让人以为已经尽力了」*。

最后这一条最有意思，而且它的适用范围远远超出这个代码库。未知错误恰恰是「重试」最诱人、同时最没有依据的那种情况 —— 因为「未知」的定义就是：你没有任何证据表明下一次尝试会和这一次不同。更糟的是它的失败方式是无声的：用户看到五条路由被挨个试过，于是认为系统已经穷尽了所有选项。它并没有穷尽，它只是**表演**了穷尽。

一个在未知错误上自动重试的系统，它没有重试策略，它只有一个带计数器的循环。

### 怎么走这张名单

```ts
const skip = [args.current, ...(args.tried ?? [])];
const at = args.order.findIndex((r) => sameRoute(r, args.current));
const ordered = at < 0 ? args.order : [...args.order.slice(at + 1), ...args.order.slice(0, at)];
const route = ordered.find(
  (r) => !skip.some((s) => sameRoute(s, r)) && dispatchable(args.health[r.profileId]?.[r.model]),
);
```

从当前这条的下一位开始，绕一圈，回到它前面为止。本次任务里已经试过的不再试，所以一个任务最多把名单走一遍 —— 不会在两条交替失败的路由之间来回打转。健康状态只当过滤器用，从不当排序依据。

一条路由是 `{ profileId, model }`：同一个模型挂在两份凭据下面是两条路由。这不是咬文嚼字。额度是按凭据计的，所以一个刚在 key A 上撞到上限的模型，在 key B 上可能立刻就能用；一个只按模型名做键的设计，恰恰表达不了最常见的那一种恢复。

## 1.2 从内容派生的幂等键，而不是从位置

`electron/tools/index.cjs`。这块是让交接变得安全的东西，而它之所以存在，是因为一个只有在有了交接之后才会出现的 bug。

账本原来按位置做键：`runId:${round}-${i}-${call.id}` —— 轮次、批内序号、模型自己生成的调用 id。一个模型从头跑到尾的时候，这把键没问题。可换一个模型接手的那一刻，**这三样全变了。** 同一件事，新的键，于是账本对「这个操作做过没有」的回答永远是「没做过」。

自动交接正是建立在这个回答上的。答错一次，就是一次重复推送、一次重复建 issue、一次重复的不可逆外部动作。

所以另存一份按内容派生的编号：

```js
function canonical(value) {
  if (Array.isArray(value)) return value.map(canonical);
  if (value && typeof value === 'object') {
    const out = {};
    for (const key of Object.keys(value).sort()) out[key] = canonical(value[key]);
    return out;
  }
  return value;
}
function opKeyOf(name, args) {
  return crypto.createHash('sha256')
    .update(JSON.stringify({ name, args: canonical(args && typeof args === 'object' ? args : {}) }))
    .digest('hex');
}
```

做的是同一件事，不管谁在哪一轮发起，编号都一样。参数先递归按键排序再哈希，因为不同模型序列化同一组参数时字段顺序可能不同 —— 不排序就等于白记。**数组保持原序**，因为顺序在数组里是有意义的。

### onceOnly：这张表刻意只有两条

```js
function onceOnly(name, args) {
  if (name === 'github_api') return String(args.method || 'GET').toUpperCase() !== 'GET';
  if (name === 'project_memory_write') return args.mode !== 'replace';
  return false;
}
```

**不在**这张表上的东西比在上面的更重要。

- **`run_command` 不在。** 同一条 `npm test` 本来就该重跑。拦住它、把上一次的旧结果当成这一次的答案，比重复执行**更**危险 —— 因为调用方会拿着过期状态当成当前状态往下推理。
- **`write_file` / `edit_file` 不在。** 同样内容写第二遍是幂等的，拦截它一点好处也没有。
- **`project_memory_write` 的 `mode: 'replace'` 不在**，同理：replace 是幂等的，append 不是。

剩下的是很窄的一类：**同样的参数发第二遍，世界上就真的多了一件事** —— 一次非 GET 的 GitHub API 调用，一次追加式的记忆写入。

这是去重规则该有的形状，也是大多数系统会做反的地方。人的直觉是「默认去重、按需豁免」，而那会造出一个默默返回过期结果的系统。这里默认是执行，抑制是逐个操作显式加进来的，而且每一条都写了理由。

拦下一次重复的时候，返回的不是一个静默的 no-op：

```js
return { ok: false, content: '', repeated: { at: done.at, callId: done.callId },
  error: `这次任务里已经做过完全相同的操作（调用 ${done.callId}），本次没有重复执行。
          需要那次的结果就去读它；确实要再做一遍，请改变参数或说明理由，由用户确认。` };
```

模型被告知发生了什么、上一次的结果在哪、以及要覆盖这个决定需要做什么。静默成功会教会它这个操作很便宜；静默失败会教会它重试。

还有第三种状态，而且它最要紧。当账本说某个操作**已经开始**但没有可靠的完成记录时（中断的运行、被杀掉的进程），工具返回 `uncertain: true` 并且拒绝猜：

> 这一步在中断前已开始，但没有可靠的完成记录。请先核实外部结果，再选择跳过或明确允许重试，避免重复操作。

三种状态，不是两种：做了、没做、**不知道**。这个区分在这个系统的每一层都会再出现一次，它是整个代码库里重复得最多的一个想法。

## 1.3 钩子：刻意不能从仓库里读的配置

`electron/hooks.cjs`。一个会改变状态的工具执行成功之后，跑一条检查命令；没通过就把它的输出摆到模型面前，就在这一轮。

前提写在头部注释里：`AGENTS.md` 里那堆「必须做」—— 版本号三处同步、不覆盖已有 tag、合并前 diff 基线 —— 作为文字，只是写给模型看的指令。*模型忘了就是忘了，而且它忘了没人知道。* 钩子把其中确定性的那部分变成程序行为。

三个选择，都是防御性的：

**配置只从应用设置读，绝不从工作目录读。**

```js
function readHooks() {
  try {
    const raw = store.kvGet(SETTINGS_KEY);   // 'snc:settings:v1'
    const list = raw ? JSON.parse(raw).hooks : null;
    return Array.isArray(list) ? list : [];
  } catch { return []; }
}
```

把钩子放在仓库里（`.wickrun/hooks.json` 之类）方便得多，同类工具也确实是这么做的。源码用一句话否决了它：*那等于让任何一个被克隆下来的仓库都能在这台机器上自动执行命令。* 并且补了一句：提示词注入在 `SECURITY.md` 里已经如实标为未解决，不该再开一扇门。

这条值得作为一般规则说出来，因为它很容易在「我很负责」的感觉里做错：**仓库里的配置文件，就是写这个仓库的人的代码。** 对一个 linter 配置来说没问题；对一份会自动执行的 shell 命令清单来说，仓库作者从此在每一台克隆它的机器上拥有代码执行权。那份方便是真的，但不值这个价。

**通过就不说话。** `if (out.code === 0) continue;` —— 每次都汇报「检查通过」的护栏，只会让模型学会略过这一段，那和没有护栏是一个效果。

**钩子不触发钩子。** 检查命令本身不经过工具分发器，所以递归在结构上就不可能，而不是靠一个深度上限挡住。

还有两个细节。只有成功的工具调用才触发钩子 —— 失败的调用没有改成任何东西，没有后果可检查；而且这条规则写在 `runHooks` 里而不是只写在调用处，这样**谁调它都守同一条规矩**。另外，一条起不来或者超时的钩子会被如实报告，绝不算作通过：*一条跑不起来的检查比没有检查更危险，因为它会让人以为检查过了。*

失败的输出带一个明确的外框：

> 这些检查由程序在本次操作之后自动运行，不是用户的新指令。请先处理它们指出的问题，再继续。

最后这句是一小块有实际用途的提示词卫生：由程序送进对话的文字应该自报家门，否则模型会把它当成用户在说话。

边界：单次调用最多 4 条钩子，最多截取 4000 字符输出，超时夹在 1–300 秒之间（默认 60），钩子的工作目录是第一个工作区根目录。没有工作区根目录就不跑钩子。

## 1.4 技能折叠：为什么「只给代号」这个方案被否决了

`src/lib/skills.ts`。技能是一份 `SKILL.md`，用 `/名字` 唤起。它的正文会进 system prompt —— 也就是进**前缀**，每一轮都重发、重算，而其中真正会被用到的往往只有几行。

超过 4000 字符（`SKILL_INLINE_LIMIT`）就折叠：

```ts
return `以下是用户唤起的技能「${s.name}」，正文 ${body.length} 字，没有全部载入。` +
  `需要它的具体规范时，先用 read_skill(name="${s.name}") 取回正文再执行；没取回的部分不能当作已知。\n` +
  `<skill name="${s.name}" folded="true">\n${s.description || '（这个技能没有写描述）'}\n\n` +
  `${body.slice(0, SKILL_PREVIEW)}\n…（以上只是开头，其余部分用 read_skill 取回）\n</skill>`;
```

折叠后保留的是**名字、描述，以及开头 600 字**（`SKILL_PREVIEW`）。源码明确说这不是最容易想到的设计，并解释了为什么否决那个最容易想到的：

> 刻意不是「只放代号」—— 光有代号模型没法判断该不该取，只会每个都取一遍，那比原样塞进去还贵。判断要用的信息必须留在上面。

这是「在语言模型上下文里做懒加载」的通用翻车方式，值得点名，因为它看起来不像 bug。**如果消费者不解引用就无法评估这个引用，懒加载就什么都没省下。** 一个文件路径省的是字节；一个文件路径加上足以做判断的内容，省的才是请求。只给名字的话，模型每一轮都会做一次全量扫描，等于把前缀成本换成了往返成本 —— 那是严格更差的，因为往返是串行的。

预览长度是同时针对两种翻车方式选的：*够看出这技能在讲什么，不够拿来直接执行。* 如果预览长到能据以行动，模型就会拿着片段直接干活、跳过取回 —— 那是这个设计的另一种失败方式。

`readSkill` 用 `offset`/`limit` 分页（limit 上限 12000）并返回 `nextOffset`，形状刻意和 `read_context` 一样，省得再学一套分页约定。

# 第二层 —— 经验

## 2.1 观测记录，以及它要修的那个问题

`src/lib/observations.ts` 自己描述过一个很具体的病症：

> 观测到今天为止是只写不读的：九十天、几百条任务、带用户反馈的完整轨迹，没有一条路径回到下一次决策。

这是一个没有分析后端的应用里，遥测数据的常态：它在积累，它从来没被读过，而所有人都以为它在起作用。

`src/lib/routing-memory.ts` 把它聚合成三个数：**做成率、端到端活跃耗时、每成功单位成本。** 头部注释点明了聚合工作的约束 —— *照搬，不自造指标* —— 并列出三条取数约束，每一条注释都归因到一次真实测试里踩出来的坑。

## 2.2 统计单元是哈希后的路由别名

不是模型名。别名由模型、凭据和端点共同派生：

```ts
export async function routeAliasOf(model, profileId, routeKey, epoch) {
  return routeAlias(model + '::' + profileId + '::' + routeKey, epoch);
}
async function routeAlias(url, epoch) {
  const hash = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(epoch + '::' + url));
  return 'route-' + [...new Uint8Array(hash)].slice(0, 8).map(x => x.toString(16).padStart(2, '0')).join('');
}
```

两个互相独立的理由。

**网关。** `auto/best-coding` 这种逻辑路由算它自己一条。网关背后实际执行的是谁，随时可能变，所以把这次运行的结果归到某个底座模型头上根本就是错的 —— 你观测到的不是那个模型，是网关的选择。下一次你能作用于的东西是那个网关条目，所以被度量的就该是它。

**观测里不存明文路由。** 存的是哈希。别名之所以导出，是为了让界面能把「接力名单里的候选」和「记分表里的行」用同一套算法重算一遍对上号 —— 它不能反解，不可逆是有意的。`epoch` 这个盐意味着清空统计之后，旧记录真正成了孤儿，而不是留在那里等着被重新关联。

## 2.3 三个桶，因为两个就是在撒谎

```ts
export function verdictOf(t: TaskObservation): Verdict {
  const fb = t.feedback?.outcome;
  if (fb === 'usable') return 'done';
  if (fb === 'partial' || fb === 'unresolved') return 'not_done';
  const a = t.acceptance;
  if (a.failed > 0) return 'not_done';
  if (t.status === 'completed' && a.total > 0 && a.passed === a.total && a.program > 0) return 'done';
  return 'unknown';
}
```

有用户反馈时，用户反馈最硬。没有反馈时，只有「声明了验收、全部通过、**而且至少有一条是程序核验的**」（`a.program > 0`）才算做成。

最后这个条件是吃劲的。模型自己复核通过不算独立验证。下发给模型的指令里就这么写着；统计的时候要是又把它算成功，等于一只手写下的规矩被另一只手拿掉，算出来的数字叫「做成率」，实际是「模型宣称自己做对的频率」。

其余一律 `unknown` —— 不猜。

`doneRate` 的分母只有 `done + notDone`。`unknown` 单独带着、单独一列报出来，从不折进任何一边。源码给了实测数据：**只有大约四分之一的任务有用户反馈，剩下四分之三既不能算成功也不能算失败。** 把 75% 的数据塞进任何一边，得到的不是一个近似值，而是一个伪造值 —— 而且因为它是朝一个固定方向伪造的，它看起来会很稳定，那比看起来很吵还糟。

又是三个状态而不是两个。记分这里是 `done / not_done / unknown`，工具账本那里是 `completed / not_started / uncertain`，同步合并那里会是 `本地 / 远端 / 说不清`。

## 2.4 样本门槛，以及不够的时候给什么

```ts
export const MIN_RANK_SAMPLES = 8;   // 低于这个样本量不排名
export const MIN_COST_SAMPLES = 20;  // 成本数字更不稳，门槛更高
```

判得出的样本不到八条时，`doneRate` 是 `null`，**不是 `0`**。这个区别就是全部要点：`0` 是一个关于这条路由的断言，`null` 是没有断言。`tokensPerDone` 还额外要求 20 条判定样本、至少一次成功、而且用量记账没有缺口（`costIncomplete`）—— 因为有请求没记到用量的路由，会算出一个自信而错误的成本数字。

`medianActiveMs` 用中位数不用均值，因为一条长尾任务就能把均值拉废。

`falseDoneRate` 量的是另一件更有意思的事：**声称完成、但验收里还有没过、没核验或核验不了的任务占比。** 也就是这条路由「告诉你它做完了而其实没有」的频率。

排序（`routeScores`）：能排名的按做成率降序在前，不能排名的按样本量降序排在后面 —— 是排队等着攒够，不是被判了刑。

## 2.5 产出是一个按钮

`src/components/FailoverList.tsx`：

```ts
const rankable = routes.filter((r) => scoreOf(r)?.doneRate != null);
const suggested = (() => {
  const sorted = [...rankable].sort((a, b) => (scoreOf(b)!.doneRate ?? 0) - (scoreOf(a)!.doneRate ?? 0));
  let i = 0;
  return routes.map((r) => (scoreOf(r)?.doneRate != null ? sorted[i++] : r));
})();
```

这个置换要仔细读，它编码了一个主张：**只有那些「样本够、判得出」的路由所占的位置被重新排列**，样本不足的路由停在用户放它的地方一动不动。源码注释：

> 排序建议：只动「样本够、判得出」的那些，样本不足的留在原位。把没数据的一律挤到后面，等于让「没被用过」变成「不好」—— 那是编造。

这是整个系统所围绕的那条界线最干净的一次表述。**排序就是下结论。** 把一个没被度量过的东西排到最后，是在对它下一个你没有任何证据的结论，而且这个结论会自我实现：被排到后面的路由永远不会被选中，永远攒不到样本，也就永远逃不出那个「因为没有样本而得到的」排名。最容易写的那种实现 —— 全排、null 放最后 —— 会悄悄造出一个长得像数据的陷阱。

而且这个按钮必须由人来点。按钮下面那行字写着：*这是建议，不是自动执行：顺序仍然由你定。样本不足的保持原位，不会被历史数据挤到后面去。*

# 第三层 —— 元

## 3.1 专门用来不信任前两层的那一层

`src/lib/evals.ts` 一上来就说明了它为什么存在：

> 这一层是防止前面几层自欺的安全带。路由记分、技能成败、纠错留存都会产生「看起来在变好」的数字，而验证它们的唯一办法，是拿一组**固定的**任务在不同配置下各跑一遍，比同一把尺子。

这是对「从自己的轨迹里学习」这类系统的问题的诚实表述：轨迹变了，样本总体也跟着变了。配置改完之后做成率上升，这件事本身什么也说明不了，因为那批任务已经不是同一批任务了。**固定不变的题目是唯一能量到系统本身、而不是量到这一周的仪器。**

题目来自真实失败。`worthKeeping` 只接受 `verdictOf(t) === 'not_done'` 的观测 —— 成功的题目没有区分度 —— 一条失败的任务可以一键存成回归题。任务原文原样保存：*不改写，改写过的就不是当初那道题了。*

## 3.2 dev / holdout，以及 holdout 会退化

```ts
export const HOLDOUT_STALE_USES = 3;
export function staleHoldout(cases: EvalCase[]): EvalCase[] {
  return cases.filter((c) => c.split === 'holdout' && c.uses >= HOLDOUT_STALE_USES);
}
```

两个切分。新题默认进 `dev`：*一上来就进 holdout，等于还没看过就宣布它是留出集，而你马上就会去看它。*

一般实现不会做的那部分是：**holdout 会退化。** 每道题记自己的 `uses`，超过三次 `staleHoldout` 就把它标出来该轮换了。理由是：一道你已经拿来调过的题目，它已经是开发数据了，再拿它验收只是在量自己的过拟合。这件事没法在类型层面强制 —— 也强制不了 —— 所以计数存在题目自己身上，退化状态被摆到台面上，这是程序面对一个执意要继续用陈旧 holdout 的人所能做的全部。

`report(store, split)` 绝不混着算两个切分，并且对「同一道题同一个配置」只取最近一次结果，所以反复重跑不会稀释结果。

## 3.3 preserve-and-extend

```ts
const regressed = shared.filter((id) => base.get(id)!.done && !cand.get(id)!.done);
const gained    = shared.filter((id) => !base.get(id)!.done && cand.get(id)!.done);
return { regressed, gained, compared: shared.length,
         adopt: shared.length > 0 && regressed.length === 0 && gained.length > 0 };
```

采纳契约：一个候选要被采用，必须至少在一道题上有收益、**在任何一道题上都没有退步**，而且和基线有共同跑过的题目。

不是「平均分更高」。源码：

> 只看平均分会让「修好两个、弄坏一个」看起来是净赚，但那一个退步的恰恰是之前已经能做对的事 —— 用户会先注意到它坏了，而不是别的好了。

这是一个比平均分更强、也更脆的判据，而这两个性质都是有意的。严格不退步的采纳有时会卡住不动；这是特性，因为另一种选择是一个在总量上持续往前棘轮、同时在边缘不断掉能力的系统 —— 那是「在异质任务分布上优化任何单一标量」的经典翻车方式。**平均分是一个标量；逐题否决权不是。**

源码把这个契约归于 DarwinX，把「失败任务进测试集」这条流水线描述为 Meta 的一条内部实践；这两处出处是源码写的，此处照录，未独立核实。

回归跑的判定用的是和路由记分完全一样的规则：完成、全部要求通过、至少一条是程序核验的。注释直接点了原因：跑回归题时*没人守在旁边一条条点*，所以没有用户反馈可退。要是在这里退而求其次去认模型自评，回归集就会变成「模型说自己做对了多少次」的统计。

# 2.9.0 —— 把经验层带到另一台机器上

经验层是在一台机器上积累起来的。只有当它能在你换新笔记本时活下来，它才值点什么。2.9.0 让它可以搬走，而真正有意思的工程全在**什么东西不搬**上。

## 4.1 安全边界只有一个文件

`src/lib/sync-policy.ts` 自述了它的角色：

> 这个文件是整条同步链路里唯一的安全边界。合并算法写错了，最坏是数据乱；这里写错了，是把 API key 或者一条能在别人电脑上执行的命令送了出去。

所以它是**白名单制**，而且头部注释是从「失败方向」这个角度给的理由：没在 `SYNC_KEYS` 里的一律不同步，没在 `SYNCABLE_SETTINGS` 里的设置字段一律不出门。新增字段默认「不同步」，*这样忘了改这里的后果是「少同步了一样东西」，而不是「多泄露了一样东西」。*

这是任何放行/拒绝决策都该有的默认，而它被选中的次数出奇地少 —— 因为黑名单更好写，而这个选择的代价要等到第一个被忘掉的字段出现时才显形。

同步的是：会话、项目、技能、定时任务、观测记录，以及设置里经过过滤的一个子集（14 个字段）。白名单旁边还有两张纯文档性质的表 —— `NEVER_SYNC_KEYS` 和 `DEVICE_LOCAL_SETTINGS` —— 存在的唯一目的是给**理由**一个安放的地方：*列在这里不是为了实现（白名单本来就不含它们），是为了让「为什么不同步」有个地方写下来，以后有人想加进去时先看见理由。*

摘几条原文：

- `snc:remote:token` —— *遥控配对令牌：同步出去等于复制入口钥匙*（复制到每一个同步落点：网盘、U 盘、中转目录）。
- `snc:device:id` —— *设备编号：每台机器一个，同步过去两台会抢同一个落点文件*。
- `tools` —— *工作目录、claudeBin、Chrome 端口都是本机路径，另一台机器上根本不存在*。
- `modelHealth` —— *路由健康：记的是「从这台机器出去通不通」，换个网络结论就不一样*。
- `grantLedger` —— *授权台账：记的是这台机器上批准过什么，是本机的审计记录*。

## 4.2 为什么密钥不同步，以及为什么它不是一个开关

```ts
export const SECRETS_NEVER_SYNC = true;
```

没有开关，源码也说不打算做开关。理由不是「密钥很敏感」—— 那会是一个「加密得更狠一点」的理由。它是结构性的：

> API key 经 safeStorage 加密，密钥材料绑这台机器的系统身份（Windows DPAPI / macOS Keychain / Linux libsecret）—— 密文搬到另一台机器上本来就解不开，硬要同步就只能先解密成明文再发出去，那就正好把 BYOK「密钥不离开本机」这条前提推翻了。

所以这里的问题不是「有多大泄露风险，值不值得权衡」，而是**实现这个功能本身就要求做一遍产品承诺不做的那件事**。源码给的两条替代路径都让密钥留在原地：另一台设备自己填一个 key，或者用遥控把工具调用转发回第一台执行。

`stripProfileSecrets` 只带凭据档案的**结构**出门 —— 名字、地址、附加头、路由偏好 —— 无条件把 `hasSecret` 置为 `false`，并过滤掉凭据形状的附加头。*对面那台机器有没有这条 key，由它自己的 secrets 桶说了算，不由同步包说了算。*

## 4.3 为什么钩子不同步

源码里的理由是一句话，值得原样抄下来：

> 注意 hooks 不在里面，而且是故意的：钩子的内容是一条命令行，会在工具成功后自动执行。同步钩子意味着任何能往同步落点写东西的人，都能让一条命令在你的桌面上跑起来 —— 那是一条从「能写文件」到「能执行代码」的升级路径。换设备时钩子请手动重配，几条而已。

这和 §1.3 是同一条规则，只是往外推了一层。§1.3 里不可信的来源是一个被克隆下来的仓库；这里是一个共享文件夹。两种情况都归结为：**一份钩子清单就是可执行内容，所以钩子清单能从哪里来，代码就能从哪里来。** 同步的设计和钩子的设计是刻意保持一致的 —— 这就是为什么 `hooks` 既不在 `SYNCABLE_SETTINGS` 里，又带着理由被列在 `DEVICE_LOCAL_SETTINGS` 中。

## 4.4 两道失效方式不同的网

白名单按字段名过滤。第二道网扫描值：

```ts
export const SENSITIVE_FIELD =
  /^(?:api[_-]?key|access[_-]?token|refresh[_-]?token|auth[_-]?token|authorization|password|client[_-]?secret|secret|token|cookie|set-cookie)$/i;

export function assertSyncSafe(payload: unknown): void {
  const leaks = findSensitivePaths(payload);
  if (leaks.length) throw new Error(`同步包里出现了凭据字段，已中止：${leaks.slice(0, 5).join('、')}`);
}
```

源码说清了为什么两道都要：*白名单挡的是「字段名」，而密钥可能哪天被人塞进一个白名单里的对象深处。两道网的失效方式不一样，这才叫两道网。* `assertSyncSafe` 是抛异常 —— 它中止同步而不是洗一洗继续，因为**一个需要被洗的包本身就是上游出了问题的证据**。

这个正则和 `electron/data-backup.cjs` 里的 `sensitive` 保持逐字一致，`tests/sync-policy.test.cjs` 会逐字比对这两处，防止其中一边悄悄放宽。

收包时 `graftDeviceLocal` 的顺序是：先铺本地，再盖同步来的白名单字段，最后再把本机字段盖回来 —— *不管同步包里写了什么，本机字段永远赢。* 一个被夹带进包里的 `remote.token` 或者一条 `hooks`，在到达任何地方之前就已经被本地值覆盖掉了。`hasSecret` 同样以本机为准：同步包永远说 `false`，但这台机器自己可能真有这条 key。

## 4.5 合并：确定性高于正确性

`src/lib/sync-merge.ts` 把目标定义为：两台设备互相同步之后，双方手里的东西必须一模一样，**而且跟「谁先合并、合并了几次」无关。** 其余一切都服从这一条：

> - 时间戳大的赢
> - 时间戳一样就比内容，内容序列化后字典序小的赢
>
> 第二条看起来很随意，它的作用不是「选对」，是「两边选得一样」。时间戳撞车本来就无从判断谁新，随便挑一个但两边挑得一致，胜过各挑各的。

对一个没有权威方的系统来说这是正确的优先级，而把它明说出来并不常见。**收敛是可以检验的性质；「在时间戳撞车时选对」这件事甚至没有定义。** 一个任意但全序的 tie-break 给你一个能测的性质；一个试图聪明的 tie-break 两样都给不了。

时钟被明确地不信任，也被明确地不去纠正：*纠正需要一个权威时钟，而这套东西没有服务器。* 能做的是把影响限制住 —— **合并一律逐条进行，从来没有整份替换** —— 所以一台设备的时钟偏了，最坏是单条记录选错版本，而不是让一份旧库把当前的盖掉。

`canonical()` 先排键再序列化，保证两台设备算出同一个字符串。输出按 id 排序，所以合并后的状态在两边逐字节相同。

## 4.6 墓碑，以及为什么一次删除会输给一次更晚的编辑

没有删除标记的话，在一台机器上删掉的东西会被另一台原样同步回来。所以删除留下墓碑 `{ id, deletedAt, by? }`，其中 `by` 只用于排查，**不参与任何判定**。

这里有两个和直觉相反的选择。

**两台机器都删过同一条时，合并保留的是更早的那次删除时间。**

```ts
if (!prev || t.deletedAt < prev.deletedAt) graves.set(t.id, t);
```

> 取早的而不是取晚的，是因为「删除发生在什么时候」决定了它能不能压住一次编辑，取早的更保守 —— 编辑更容易赢，数据更不容易丢。

**一次删除会输给任何发生在它之后的编辑。**

```ts
if (stampOf(item) > grave.deletedAt) {
  graves.delete(id);       // 删除之后又改过 —— 那次编辑是更晚的意图
  items.push(item);        // 记录复活，墓碑作废
}
```

两个选择是朝同一个方向偏的，而这个偏斜本身就是论证：**两种错误的代价不对等。** 一次没传播出去的删除，留给你的是一条再花两秒钟删一次的记录；一次输给了删除的编辑，是一份哪里都不再存在的工作。既然如此，含糊的时候就该每一次都判给编辑 —— 「取更早的删除时间」和「编辑复活记录」这两条规则，都是把这份含糊朝那个方向花掉的方式。

墓碑保留 90 天，和观测记录的保留期一致，长 TTL 的理由也写着：*清早了会让一条老记录从另一台设备复活，所以 TTL 要比两台设备之间可能的最长失联时间宽。*

## 4.7 观测记录不按普通集合合并

```ts
droppedTasks:  Math.max(local.droppedTasks  ?? 0, remote.droppedTasks  ?? 0),
writeFailures: Math.max(local.writeFailures ?? 0, remote.writeFailures ?? 0),
```

tasks 逐条合是对的，但计数器不能相加：**同一份数据同步两次就会翻倍，而这些数字是给「路由做成率」当分母用的。** 分母翻倍，等于把经验层得出的每一个结论都悄悄改写一遍。它们本来就是单调递增的本地计数，取 max 至少不会凭空变大。

`ignoredRecordIds` 取并集 —— *任何一台设备说「这条别算」，就都别算。* `epoch` 不合并，本地永远赢，因为*epoch 换了代表用户清过记录，清记录是一个明确的本地意图，不该被另一台设备撤销。*

设置整份取新，不做字段级合并：

> 设置里的字段互相之间有约束（比如 failover 列表引用 keyProfiles 里的 id）。逐字段各取各的新值，能拼出一份两边都没有出现过、而且自相矛盾的设置。整体取新虽然会丢掉另一边的改动，但至少丢掉的是一份自洽的旧设置。

## 4.8 信封

`electron/sync-crypto.cjs`：口令至少 12 位，经 scrypt（N=2¹⁵、r=8、p=1、32 字节密钥）派生，再用 AES-256-GCM 封装，每个包一份新的 16 字节 salt 和 12 字节 nonce。format、version、salt、nonce 一起作为 AAD 绑进去，*因为不绑的话，改包头（比如把版本号改小，诱导旧解析路径）不会破坏 tag，那等于留了一条降级攻击的路。* KDF 参数写进包头，这样以后调参了，旧包还能按它自己的参数解开。

封好的包上限 64 MB，防止一个畸形包把内存吃光。忘了口令没有找回途径，源码说以后也不会有：*有后门的话，后门就是整套东西的实际安全等级。*

落点（`electron/sync-folder.cjs`）是一个文件夹而不是服务器，*因为再自建一个收全部对话的服务器，等于把刚拒绝掉的信任又请回来。* 每台设备只写自己那一个文件 `<deviceId>.wsync`，设备号是随机 UUID、不含任何机器信息，*因为文件名会躺在落点上被人看见。* 设备之间从不写对方的文件，所以文件夹里压根不存在写冲突；合并发生在读到之后，在各自的机器上。落点必须是绝对路径，而且不跟符号链接。

## 4.9 同一版里被收紧的遥控入口

`electron/remote-server.cjs` 把来源地址分档：`loopback`、`private`（10/8、172.16/12、192.168/16、IPv6 `fc00::/7`）、`cgnat`（100.64.0.0/10）、`linklocal`（169.254/16、`fe80::`）、`public`、`unknown`。只放行前四档。来自公网的连接在 socket 层直接掐断，不回任何东西 —— *不回 401、不回 403，什么都不回；扫端口的人得不到「这里有东西」的任何信号。*

头部注释把这个 bug 说得很直白：

> 以前这里的注释写的是「默认只绑内网地址」，但代码一直是 `listen(port, '0.0.0.0')` —— 绑的是所有网卡。在路由器后面它们的效果一样，可这台机器一旦拿到公网 IP，或者插进咖啡店的公共 Wi-Fi，`0.0.0.0` 就是把一个能跑命令行的入口摆在门口。

绑定继续保持 `0.0.0.0`，因为 Tailscale / WireGuard 的虚拟网卡也得能进来，而那些网卡的地址是会变的。修复放在连接层。CGNAT 在放行名单里正是因为 Tailscale 的 tailnet 地址发在 `100.64.0.0/10`，这就是「装 Tailscale」这条方案**一行代码都不用改**就生效的原因 —— 而设置界面现在会把每条地址标上档位（私有网络 / 局域网 / 链路本地 / 本机），让正确答案直接写在界面上而不是埋在文档里。回环也在放行名单里，是有意的，为的是 Cloudflare Tunnel 和反向代理这类东西；但注释同时写明：走那条路必须自己在前面再加一层认证，Bearer token 单独一层在公网上不够。

# 五个乍看不对的决定

## 它推荐，它不替换

记分器手里有每条路由的做成率。自动应用它只要一行。但它是一个按钮，而且那个排序置换刻意让样本不足的路由留在原位。

理由不是谨慎，是**边界**。程序能量到的是完成情况。用户真正的目标函数里包括：哪条 key 是免费的、哪条是公司报销的、哪条有数据驻留约束、以及这周他正在评估哪一条。这些从轨迹里一个都观测不到。一个在它唯一能看见的那个维度上重排的系统，不是在优化用户的目标，而是在优化一个代理指标，然后把结果当成决定端上来。

而「自动排序、null 放最后」这个具体做法会造出一个长得像数据的陷阱：一条从没被用过的路由被排到最后，于是永远不会被选中，永远攒不到样本，也永远逃不出去。度量系统会亲手制造出那份用来为它自己辩护的数据。

## 「不知道」是一个桶，不是一个舍入误差

现场数据里大约四分之三的任务没有判定。把它们划给任何一边，得到的数字会是稳定的、精确的、并且是假的 —— 而稳定且精确比嘈杂更糟，因为它会骗取信任。

同样的三态形状在各处重复出现：记分里的 `done / not_done / unknown`、工具账本里的 `completed / not_started / uncertain`、验收里的 `passed / failed / unverifiable`。每一次，第三个状态都是那个携带起来最贵、最想被折叠掉的。**把它折叠掉，就是一个系统开始给自己讲故事的起点。**

## 未知错误不触发交接

重试最诱人的那种情况，恰恰是你最没有证据认为下一次会不一样的那种。而且除了白白烧掉整张名单之外，它还制造一个很具体的错觉：用户看到五条路由被试过，于是认为选项已经穷尽了。什么都没被穷尽，穷尽只是被表演了一遍。

## 一次删除会输给一次更晚的编辑

删除之后又被编辑过的记录会复活，墓碑作废。两边都删过时取更早的那次删除时间，让编辑更容易赢。

这个不对称是刻意的，因为两种错误不对称：一次没传播出去的删除，代价是两秒钟的烦躁；一次输给删除的编辑，是一份没有任何副本的工作被毁掉了。**一个没有权威方、不得不猜的分布式系统，应该朝着「猜错了还能救回来」的那个方向猜。**

## 合并里确定性高于正确性

时间戳撞车时，赢的是规范化序列化后字典序更小的那份。这不是关于哪一版更好的判断 —— 系统里没有任何东西能做这个判断。它是一个保证：两台机器会到达同一个状态。

收敛是一个你能测的性质。「在时间戳撞车时正确」连定义都没有。一个没有权威时钟的系统，就该去优化那个它真的能验证的性质，并且把这件事说出来。

# 这不是什么

- **没有任何东西改写自己的代码。** 这里的自我改进是：轨迹喂给以后的决策，再由第三层检查这个回路产出的是不是改进。机制是度量和采纳契约，不是代码生成。
- **没有任何东西无人监督地运行。** 路由记分器产出一个按钮，回归工具产出一份对比，两个都在等一个人。
- **元层之所以存在，是因为前两层很有说服力。** 任何从自己轨迹里学习的系统都会产出一批往上走的数字。`evals.ts` 就是那个追问「它们到底有没有意义」的部分，而它的采纳契约之所以是逐题否决权，正是为了让一个在上升的平均分藏不住一项已经丢掉的能力。
- **尚未验证：** Android 客户端在真机上的表现，以及部分供应商的思考强度参数映射。安装包没有代码签名。

本应用 Apache-2.0，源码在 [github.com/lifishard/wickrunAI](https://github.com/lifishard/wickrunAI)。`src/lib/failover.ts` 92 行，`src/lib/routing-memory.ts` 129 行，都短到可以整份读完；这篇文章所转述的推理，原样写在它们的注释里。
