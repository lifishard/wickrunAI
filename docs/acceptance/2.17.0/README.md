# 2.17.0 桌面验收记录

环境：Windows，真实 Electron 应用，独立 `desktop-qa` 数据目录与 `desktop-project` 测试项目。日常 wickrunAI 数据与 OpenAI 窗口保留。未发布、未替换安装。

模型侧为仅监听本机的确定性 OpenAI 兼容 HTTP 服务。除模型回答受控外，经过实际渲染界面、IPC、网络请求、运行器、主进程工具、文件隔离、快照和合并；未用测试替身替代这些应用链路。测试数据预置了两位成员和任务；项目创建、运行前检查、启动、查看差异、交付批准、合并、新模板生成/版本保存均通过应用界面操作。

## 第一轮：完整交付

1. 通过首页的协作空间入口创建“工程验收 · 2.17”。
2. 检查运行目标、权限、目录和版本，点击开始。
3. 执行成员实际写入 `result.json`，故意得到 `status: draft`，发布 v1。
4. 独立复核成员在自己的隔离目录实际读取 v1，返回 fail。
5. 执行成员收到返工项，实际改成 `status: ready`，发布 v2。
6. 复核成员收到 v2 并重新读取，返回 pass；两次引用的是不同快照编号与真实读取调用编号。
7. 应用停在“等你验收交付”；没有自动把复核通过等同于用户接受。
8. 打开文件差异，主目录显示文件不存在，隔离产物显示 ready。核对后回到运行点击“批准”，再合并执行成员产物。
9. 读回测试主目录得到有效 JSON，`status` 为 `ready`；记录最终文件 SHA-256。

对应截图：`01-preflight.png`、`02-awaiting-acceptance.png`、`03-file-diff.png`、`04-accepted.png`、`05-merged.png`。筛选后的持久记录与哈希：`desktop-evidence.json`。

## 第二轮：最终版本复查

使用界面的“生成执行与复核流程”按钮，保存为 v1，再从运行前检查启动。新流程自动绑定原任务；再次经过 fail → 返工 → pass。主目录本来已有 ready，因此执行成员的 v2 回到主目录基线，快照文件列表为空；接收端正确撤销 v1 的 draft，实际读回 ready。已同时核对两个隔离目录。这验证了版本归零在桌面路径中的行为。截图 `07-review-history.png` 展示两次复核状态。

全量自动化最终 **609/609 通过**，见 `automated-tests.txt`；类型检查及构建通过，见 `build.txt`。构建仍提示现有大包体积警告。

## 发现并修复

- 复核副本原来也显示合并按钮，容易重复交付。已隐藏该动作并加用途说明。最终构建实查截图：`06-final-review-copy.png`。
- 运行详情新增复核 verdict 和产物版本说明；生成流程会绑定原任务。
- 验证产物时同时核对发布者版本与接收副本，阻止接收后被修改的副本沿用旧结论。
- 受控 HTTP 服务启动时 `/models` 返回空体导致一次读取模型列表报错；这是测试服务器缺少 GET 路由，已补齐夹具，任务请求与首次闭环未受影响。

## 证据边界

- 此记录证明桌面功能链路；不证明 Claude/OpenAI 等真实模型一定能发现缺陷，也不证明多成员比单成员省钱或质量更好。
- 语义压缩保真、真实供应商认证/断流、本机订阅客户端工具证据、长任务组合质量仍未验收。
- 故障恢复与跨范围拒绝另由自动化测试覆盖；没有在日常项目中注入故障。
