# v2.16.2 · 报错要带着出路

两条都来自 2.16.1 那次 MATH 100 实测。

## 一、证据填错时，直接把能用的 callId 列出来

`complete_task` 的 `evidence` 要的是**实际成功工具调用的 callId**。实测里模型填了文件路径，连撞三次：

```
证据必须引用实际成功执行的工具 callId，不能使用计划或虚构记录。
```

报错本身没错，但它没说该填什么——而那份清单执行器手里本来就有。每撞一次都要重发整段上下文，这是真金白银，而且这一轮的轮次预算也跟着烧掉。（这次撞的三次直接导致第一段触发了「本阶段轮次已到」。）

现在报错会带上可引用的编号：

```
证据必须引用实际成功执行的工具 callId，不能使用计划或虚构记录。
可以填的编号：call-write（write_file）、call-edit（edit_file）。填编号本身，不要填文件路径或检查说明。
```

一次操作都还没做时，说的是「先真正执行一次操作，再来记录完成自查」，而不是让它换个编号再试。

同一份提示也接到了 `verify_requirements` 的 review 类证据报错上（`delivery.ts`）——两处要的是同一类编号，没道理只有一处给出路。

失败的步骤和交付闸门自己的调用（`update_requirements` / `verify_requirements` / `complete_task` 等）都不列入，它们不是执行证据。

## 二、结束节点的等待写成「等你验收交付」

2.16.0 的顶部状态条把**所有** `pendingApproval` 都写成「等你确认工具调用」，包括结束节点的交付验收门——实测截图里就是这样，会把人引到错的地方去找。现在按节点类型分开。
