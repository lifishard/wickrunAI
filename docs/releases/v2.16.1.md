# v2.16.1 · 项目设置里的下拉和勾选改不动

## 症状

「项目设置 → 权限与总预算 → 批准方式」选了新值，一失焦就弹回旧值，磁盘上的 `approvalMode` 始终不变。同一个毛病还影响：

- 项目设置里的「允许的模型接入」勾选框（两组，API 连接与本机订阅）
- 任务页的「选择已有 Workflow」下拉

同一页的数字输入框（并发上限、每次运行 tokens / 分钟）**一直是好的** —— 这条线索就是根因。

## 根因

不是存储层。存储层接受这次改动（新增用例直接证明了这点）。

问题在 `TeamRuntime.update()` 的时序：

```ts
update(id, fn){
  this.saving++; this.emit();          // ← 同步通知重渲染
  const work = this.serial.then(async () => { ... fn(p) ... });   // ← 回调排到 promise 里才跑
}
```

`emit()` 立刻触发重渲染，把受控 `<select>` / `<input type=checkbox>` 的 DOM 值按 store 里的**旧值**复位。等 `fn` 真正执行时才去读 `e.target.value`，读到的已经是复位后的旧值，于是把旧值原样写回——界面上看就是「点了没反应」，而且没有任何报错。

数字输入框写成 `const value=Number(e.target.value); if(value>0) act(update(...))`，值在调用 `update` **之前**就取出来了，所以不受影响。

## 修法

四处事件处理都改成先取值再调用 `update`：

```ts
onChange={e=>{const mode=e.target.value as ...; act(update(p=>{p.settings.approvalMode=mode;}));}}
```

## 回归测试（`tests/team-settings-write.test.cjs`，3 项）

1. 存储层接受改批准方式 —— 把根因排除在存储层之外。
2. `update` 的回调是延后跑的，**且回调执行前已经通知过一次重渲染** —— 把这个时序钉死，以后谁改 `update` 的实现都会撞到。
3. 静态检查：协作界面里不允许出现「在 `update` 回调体内读 `e.target`」的写法。

全量 **577 项**通过。
