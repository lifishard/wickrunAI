## 三、本轮新发现并已修的问题

### R11 · 项目设置里的下拉和勾选改不动（2.16.1）

**这条是你先撞上的**：批准方式选了新值，一失焦就弹回旧值，磁盘上永远不变。

根因不在存储层（存储层接受这次改动，有用例证明）。在 `TeamRuntime.update()` 的时序：

```ts
update(id, fn){
  this.saving++; this.emit();                    // ← 同步触发重渲染
  const work = this.serial.then(async()=>{ ...fn(p)... });  // ← 回调延后才跑
}
```

`emit()` 立刻把受控 `<select>` / `<input type=checkbox>` 的 DOM 值按 store 里的**旧值**复位；等 `fn` 真跑起来才去读 `e.target.value`，读到的已经是复位后的旧值，于是把旧值原样写回。界面上就是「点了没反应」，**而且一句报错都没有**。

同一个毛病影响四处：批准方式下拉、允许的模型接入两组勾选框、任务页的「选择已有 Workflow」下拉。同页的数字输入框一直是好的——因为它本来就 `const value=Number(e.target.value)` 先取值再调 update。这条对比就是定位线索。

**修法**：四处都改成先取值再调 `update`。
**测试**：3 项——存储层接受改动（排除存储层）、`update` 回调延后且执行前已重渲染（把时序钉死）、静态检查禁止再出现「在 update 回调里读 e.target」。
**实测验证**：本轮用修好的版本改批准方式、选流程，都一次就成。

### R12 · 证据填错时报错不给出路（2.16.2）

`complete_task` 的 evidence 要 callId，模型填了文件路径，撞三次：

```
证据必须引用实际成功执行的工具 callId，不能使用计划或虚构记录。
```

报错没错，但它没说该填什么——而那份清单执行器手里就有。每撞一次重发整段上下文，第一段的轮次预算就是这么烧完的。

**修法**：报错带上可引用编号 `call-write（write_file）、call-edit（edit_file）`，并明说「填编号本身，不要填文件路径或检查说明」；一次操作都没做时说的是「先真正执行一次操作」。同一提示接到 `verify_requirements` 的 review 类证据报错上。失败步骤和交付闸门自己的调用不列入。
