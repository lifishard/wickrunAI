## P1：先打通两位成员的产物与证据闭环

### 1. 明确交接产物

当前 `runMember` 按 runId/memberId 创建隔离副本，副本来自主目录；`sources` 传递前置节点的文字输出。`inputRefs` 选择的是节点输出，没有看到这条路径将 A 未合并的文件版本交给 B。

这意味着不能假设 B 在自己的工作目录里能看到 A 刚生成的文件。这个结论来自代码路径检查，尚未运行双成员桌面复现。

建议最小实现：允许后续节点通过明确授权读取上游产物快照，记录产物 ID、生成节点、相对路径、版本/哈希；复核默认只读。无需开放所有成员互写目录。

验收任务：A 新增一个主目录不存在的 JSON；B 读取 A 的该版本，发现预置错误；A 修复；B 复核新版本；最终人工验收并合并。B 不能因读到旧副本而给出通过结论。

### 2. 收紧独立 review 节点

位置：`src/lib/team-runtime.ts:324`。目前分支判定接受 `verdict=pass` 和 truthy `evidence`，未在此入口验证证据引用与产物版本。

必须区分两个机制：执行 Agent 内部的 `verify_requirements` 已有程序检查与模型复核区分；流程里的独立 `review` 节点仍主要解析模型文本。今天的单成员试点不能证明后一条路径通过。

建议：复用现有验收基础，关联实际 requirement、工具检查记录及产物版本；保留 passed / failed / unverifiable；模型意见与程序验证分开显示。文件变化后旧结论不得直接复用。

验收：伪造证据、无关证据、过期版本均不能走通过分支；真实错误能驱动返工；修复后重新核验。

## 架构工作线：初始建议的完整纳入

以下“基础”仅指已查阅模块和既有资料支持的事实；“增量”是需要实现或进一步审计的范围。有基础不等于所有入口已统一，也不等于下列验收已经通过。

### A1 · 独立且持久的任务状态

- **基础**：已有 RunState、TeamRun、检查点、要求、里程碑与 handoff；`src/lib/handoff.ts` 已携带工作状态和证据。不是从零建立任务系统。
- **增量**：定义跨入口的最小任务契约，明确 taskId、attemptId、要求版本、授权、产物版本、验证记录、待确认操作与阻塞原因分别由谁维护。模型和后端可替换，事实记录不能依赖某段自然语言答复。通过适配器接入现有单 Agent 和 TeamRun，不立即合并所有存储结构。
- **优先级/依赖**：P1 定义契约并用于产物/证据交接；P2 渐进统一 API 与本机客户端的能力映射。无需先建设服务器或分布式系统。
- **验收**：同一任务换模型、暂停和重启后，要求修订、完成证据、未完成项与未知操作不丢失；用户只改一项要求时，可保留无关的有效成果；不因接续而新增一份逻辑任务或重复计费。旧记录无法补齐的字段保持未知。

### A2 · 分层上下文与当前有效要求

- **基础**：`context-memory.ts`、`task-context.ts` 已保留原文、提供历史检索、折叠工具材料；要求修订也已有实现。不能把“增加上下文管理”作为全新功能。
- **增量**：明确四层：当前有效约束、当前工作状态、可检索历史证据、按范围检索的长期经验。检查所有入口是否使用有效要求版本；用户原文继续保留，但被替代要求不应以当前指令身份反复注入。前置输入按依赖选择，工具和技能按任务需要加载，提供可诊断的上下文组成记录。
- **优先级/依赖**：P1 定义有效要求与来源规则；P2 调整上下文选择，依赖 A1/A3 的记录和评估。可复用已有检索，不预设必须引入向量数据库。
- **验收**：用户把英文改为中文、缩小文件范围或撤销某项要求后，续跑、子代理和复核者都遵守最新版本；仍能查到被替代原文。无关历史不随每轮无限增长；被省略的材料可定位取回，未读取部分不能标记已检查。

### A3 · 压缩质量与跨供应商可移植性

- **基础**：已有带来源的摘要、结构与大小校验、原文存档和压缩后回读文件。现有校验不能独立证明摘要忠实表达原文。
- **增量**：建立固定压缩/接力回归集，分别检查约束、矛盾、未知状态和证据引用。明确可读任务记录是跨供应商交接基础；供应商原生压缩状态只能在已确认兼容范围内复用，不能假定可跨模型后端通用。
- **优先级/依赖**：P1 立即建立回归基线，与故障接力验证共同推进；P2 根据失败案例改压缩策略；原生压缩接入按具体后端能力后续评估。回归集不依赖完整内核重构。
- **验收**：至少覆盖用户纠正、否定约束、尝试未成功、已完成操作、未知外部结果、相互矛盾的证据、多次连续压缩和换模型。压缩前后检查关键状态是否一致、来源是否支持结论；保留失败样本，错误摘要不得成为不可回退的唯一记录。若做运行对照，保持任务、配置和输入一致，并记录实际用量与质量，不能只比较压缩率。

### A4 · 明确委派协议与适度调度

- **基础**：已有临时子代理、稳定请求键、并发限制与协作节点；不是新增一个“多 Agent”开关。
- **增量**：将目标、必要输入、产物版本、可读写范围、预算、停止条件和验收责任结构化；返回摘要、产物引用、证据与未解决事项。主 Agent 保留整合责任。工作形态至少区分单 Agent、少量独立工作者、执行者加复核者；讨论和并行按任务需要选择。
- **优先级/依赖**：P1 在双成员闭环中采用最小协议；P2 做调度策略对照。依赖产物交接与 A1，成本判断依赖 A9。
- **验收**：委派重试不会新建重复子任务；依赖未完成不提前派发；不会把同一操作交给两个成员重复执行；取消和补充要求能到达相关执行者。越权读写被阻止；子代理未交付时主任务不得凭其自述完成。并行修改需有隔离与冲突检查。

### A5 · 多层质检与停滞检测

- **基础**：已有程序检查、模型复核、用户验收区分、完成门槛及连续失败检测；独立 review 节点仍有前述缺口。
- **增量**：所有入口使用一致的证据语义，检查绑定要求和产物版本。程序可判的条件由程序判断；语义问题可使用独立上下文复核，提供目标、产物与必要来源，降低对执行者自评的依赖。记录缺陷及修复关系，区分重复检查和新证据。
- **优先级/依赖**：P1 修独立 review 并增加版本失效规则；P2 校准模型复核与停滞判断。依赖产物版本，复核与修复共用总预算。
- **验收**：伪造/无关证据不能通过；相关文件变化使相应旧验证失效；不得通过降低验收标准解除失败。同一缺陷反复出现且没有新证据时，系统换方法、返回具体阻塞或请求必要输入，不能无限互相转派。复核者误报、漏报应通过标注样本检查，模型复核不能自动升级为程序证明。

### A6 · 可追溯的工作管理界面

- **基础**：运行总览、等待类型、产物卡片、要求检查与观测记录已经存在。
- **增量**：围绕用户关心的问题组织状态：正在做什么、生成了什么、检查了什么、为什么停、需要什么输入。把执行结束、验收通过、用户接受、合并完成分别表达，并允许展开证据来源；普通用户不必阅读完整日志才能决定下一步。
- **优先级/依赖**：P1 随双成员闭环呈现当前产物与检查状态；P2 统一各入口及诊断视图。依赖 A1/A5，R14 可随同完成。
- **验收**：在运行、等待工具批准、未知结果、待验收、拒绝、合并冲突和重启后场景中，顶部状态与持久记录一致；不会把模型说完成显示为已经验收。用户能定位实际文件版本和未检查项；不伪造隐藏思考作为进度依据。

### A7 · 权限、执行环境与能力边界

- **基础**：已有成员工具授权、运行权限快照、文件副本隔离、目录约束和合并冲突检查；API 和本机客户端的权限能力并不完全相同。
- **增量**：将授权附着于具体任务、动作类别、路径与有效范围；跨成员读取产物使用明确授权。把会话记录、调用模型的循环、实际执行环境分别界定。为不同后端声明可观察/可控制能力，不能把缺少执行证据或无法强制的权限包装为已支持。进程或系统沙箱作为单独决策。
- **优先级/依赖**：P1 保证新交接接口和后端能力边界；P2 审计凭据可达性、插件/工具授权与失效；P3 在需求和成本明确后扩展执行沙箱。
- **验收**：换模型、续跑或定时唤醒不能扩大授权；任务撤销后过期审批不得生效；产物交接不开放成员间任意目录访问。复用任务授权减少不必要重复询问，同时对能力无法映射的情况准确提示。文件副本、写入锁与系统沙箱在产品和文档中明确区分。

### A8 · 副作用恢复及定时任务统一生命周期

- **基础**：已有未知结果处理、恢复检查点、部分操作去重、定时触发记录和恢复测试；今天 R4/R7 只覆盖其中部分路径。
- **增量**：梳理每种有副作用工具的“准备、已发出、已确认、结果未知”及核实方式；重试策略绑定动作语义。定时任务复用同一任务和授权体系，明确离线、补跑、重叠执行与重复触发政策。不是把所有同参数调用一律缓存去重，测试等读取当前状态的动作仍需实际执行。
- **优先级/依赖**：P1 完成 R7 与未知结果组合测试；P2 补定时和跨后端恢复。依赖 A1/A7，无需为了本地调度立即建设云服务。
- **验收**：进程在外部动作前后中断时，不虚构成功，也不盲目重发；能核实则只读核实，不能核实则保留未知并说明具体阻塞。相同触发键不会重复建任务，重启不重复累计；用户暂停不会被自动恢复规则越过；离线行为与界面说明一致。

### A9 · 全任务成本与可比较评估

- **基础**：已有总预算、预留与用量账本、观测、评估集和基线比较；原生客户端缺少统一精确用量时有保守处理。
- **增量**：分开归因执行、讨论、摘要、质检、重试的成本，实际、估算和未知不混用。以已验收结果衡量成本，保持执行结束与用户成功分离。为上下文和调度改动进行同任务对照；模型调用本身具有波动时需保留重复试验分布，不能只挑最好一次。
- **优先级/依赖**：P0 修预算冲突；P1 保留各类调用账目与基线案例；P2 用数据调整分配和调度策略。具体样本数和采用阈值在试验前确定，不能事后按结果改口径。
- **验收**：主/子 Agent、摘要、review 和重试均计入同一任务预算；恢复与晚到事件不重复累计。报告同时展示交付质量、错误完成、用量、耗时与未核验比例，保留未知；没有价格信息不推算货币成本。优化不能只因 token 减少而宣布成功。

### A10 · 长期记忆、Skills 与可回退的经验改进

- **基础**：已有项目经验、Skills、任务观察、`routing-memory.ts` 和 `evals.ts` 的开发/留出集、基线比较。今天的协作实测并未证明自动经验学习有效。
- **增量**：区分事实、偏好、经验规则与待验证假设，补齐必要的来源、项目范围、适用条件、时间/版本及失效关系；检索时只注入相关有效项。失败经历不能自动变成全局禁令，候选经验或 Skill 修改应经历验证、采用与回退。需要补哪些字段先审计现有结构，避免重复建设。
- **优先级/依赖**：P2 做记忆结构与检索质量审计，补可追溯和失效规则；P3 才考虑自动提案、受控采用。依赖 A3/A9 的质量基线，不能用模型自评作为唯一收益证据。
- **验收**：项目经验不越界串入另一项目，旧偏好不会覆盖最新明确要求；记忆可查看、纠正和撤销。候选规则在固定任务集上与基线比较，保留失败和未知，检查原有能力退步；撤销后后续任务不继续使用被撤销规则。评估集使用与轮换有记录，不能反复调同一批题后仍称其独立验证。

## 合并后的优先级与阶段出口

P0 是当前已复现的运行正确性问题；P1 是下一阶段交付所需的最小能力和证据；P2 是基于可用闭环的可靠性与效率建设；P3 是需更充分证据的扩展。优先级与时间估算不同，本计划不预设工期。

| 阶段 | 实际工作 | 必须满足的出口 |
|---|---|---|
| 第一阶段：修故障、建立共同约定 | 修预算冲突；按使用范围修本机完成判定；定义 A1 最小任务契约、A4 委派格式及 A5 证据/产物版本；建立 A3 压缩回归基线；执行 R7 受控故障测试 | 合法预算能派发、上限不被突破；故障不重复已生效操作；接口与现有结构对应清楚；回归集给出当前实际通过/失败情况 |
| 第二阶段：验证两人协作交付 | 产物快照交接、独立 review 验证；跑生成—找错—修复—复核—验收—合并，加入重启和用户纠正 | B 确实读取 A 的当前产物；预置缺陷被发现；新版本重新核验；所有未完成/未知如实保留；只有授权变更被合并 |
| 第三阶段：验证长任务连续性与效率 | A2 上下文选择、A3 压缩策略、A4 调度对照、A6 状态统一、A8 定时恢复、A9 成本评估；开始 A10 记忆审计 | 长任务经历压缩、换模型、重启和补充要求仍能接续；同任务对照能证明质量与成本取舍；旧要求/旧证据/旧经验不污染新执行 |
| 第四阶段：按证据扩展 | 进一步统一后端状态、评估原生压缩、执行沙箱、受控经验采用及复杂调度 | 每项扩展都有明确需求、对照结果、能力边界与回退办法；不能仅凭一次成功试点直接全量启用 |

前两阶段是下一次协作空间交付的范围；第三阶段是紧接着的长期任务可靠性建设，其中基线、契约及记忆结构审计可以提前准备。阶段出口优先于增加节点数量，不能为等待大型重构而延后已有故障修复。

## 设计依据与适用边界

以下为前次讨论已经查阅的公开资料，作为设计来源保留，不是对两家桌面端未公开实现的断言；本次文档修订未重新检索产品更新。

- [Anthropic：会话、执行循环与执行环境分离](https://www.anthropic.com/engineering/managed-agents)：A1/A7 的参考，公开讨论的是 Managed Agents。
- [Anthropic：上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：A2/A3 的参考。
- [OpenAI：Compaction](https://developers.openai.com/api/docs/guides/compaction)：原生压缩能力的参考；API 文档不能直接证明 ChatGPT Desktop 所有内部会话的行为。
- [OpenAI：Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) 与 [Anthropic：多 Agent Research 系统](https://www.anthropic.com/engineering/multi-agent-research-system)：A4 的参考，不保证多 Agent 对任意任务都有收益。
- [Anthropic：Agent 评估](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：A5/A9 的参考。
- [OpenAI：项目与任务组织](https://learn.chatgpt.com/docs/projects) 与 [Claude Cowork 架构](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)：A6/A7 的参考，具体能力需按平台和执行模式区别。

下一阶段的协作目标：两位成员针对同一份明确版本的产物分工，故障后保留进度，检查结论可追溯，不突破预算、不重复已生效操作。更广的架构目标同时保留：任务跨长上下文、模型、执行后端与重启持续成立，并能用可比较的证据改善记忆、调度与成本。

## 本轮新增验收门槛 U0/U1b（2026-09-20）

- 不要求具体目标才能开始探索；“规划交付”与“实际执行交付”分开保存、确认和记录。
- 流程解释必须来自将运行的固定版本，包含真正的成员、分支、返工和退出；未保存草稿不能冒充已生效流程。
- 下一轮规划必须携带已给出的回答；旧轮结束后才继续，不能因用户尚未手工验收而卡住默认单并发项目。
- 模型建议只作为可编辑文本；用户保存新的目标与完成条件后才可准备执行，工具和路由不得从建议自动导入。
- 工程与受控桌面通过不等于真实易用性通过；U0b/U0c 及余下施工顺序以 [易用性支线](COLLABORATION_USABILITY.md) 的最新排序为准。
